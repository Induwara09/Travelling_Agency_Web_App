# SmartPOS — Java 21 + MySQL Offline-First POS

A full-stack commercial POS baseline built from the accompanying **SmartPOS Complete Specification** for cafés, restaurants, small hotels, bakeries, mini marts and retail shops.

## Target runtime

- **Java:** Java SE 21 LTS. The project compiles with `maven.compiler.release=21` through Spring Boot. It is suitable for your installed **Java 21.0.12 LTS** runtime.
- **Database:** MySQL 8.x / MySQL 8.4 LTS recommended.
- **Backend:** Spring Boot 3.5.5, Spring Security, JPA/Hibernate, JavaMail, PDFBox, Apache POI.
- **Frontend:** React + TypeScript + Vite.
- **Primary deployment:** Windows 10/11 64-bit cashier PC.

## Core offline-first design

The POS does not require internet for normal checkout:

`React UI -> local Spring Boot API -> local MySQL -> local receipt printer`

Internet is used only for optional cloud synchronization, queued invoice/report email and remote services. If internet disappears during a sale, the local database remains authoritative and checkout continues.

## Working modules included

- JWT login and backend RBAC for **CASHIER / MANAGER / ADMIN**.
- Modern touch-friendly cashier POS.
- Product/category search and menu.
- Cart, quantities, cash/card/bank/wallet payment recording.
- Dine-in/takeaway/delivery order type and table number.
- Customer details during checkout.
- Inventory stock deduction inside the same database transaction as sale/payment.
- Low-stock/out-of-stock states.
- Manager/Admin override when requested quantity exceeds recorded stock.
- Immutable stock movement history.
- Product CRUD for Manager/Admin.
- Stock receive and signed stock adjustment.
- Recipe/ingredient BOM: prepared menu products can consume ingredient stock automatically.
- Supplier and purchase receiving; purchase completion updates stock and cost.
- Sales history and controlled Manager/Admin void; original financial record is retained.
- 80mm receipt rendering/printing from the local PC.
- A4 PDF invoice download generated by the Java backend.
- Invoice email queue with automatic retry when SMTP/internet becomes available.
- Cashier shift open/close and expected cash calculation.
- Dashboard and database-driven sales/inventory reports.
- CSV and Excel sales export.
- Monthly automatic sales-report email scheduler.
- Customer management.
- Held-order persistence API for local order holding/resume workflows.
- Audit logs.
- Automatic/manual MySQL backup using `mysqldump`.
- Optional cloud synchronization queue with retry and unique sale IDs.
- Windows production build/start scripts and logon auto-start task.

## Important production notes

This repository is a strong commercial baseline, not a claim that a payment-acquirer integration, fiscal/tax certification, email provider, real kitchen printer, remote cloud server or device-management provider has already been contracted. Those external integrations require the selected vendor's credentials/protocols and final on-site printer/network testing.

Before production use, test the exact receipt printer, cash drawer, card terminal, email provider, MySQL backup/restore process and Windows permissions on the target hardware.

# 2. Create the MySQL database

Open MySQL Workbench as a MySQL administrator and run:

```sql
CREATE DATABASE IF NOT EXISTS smartpos
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;

CREATE USER IF NOT EXISTS 'smartpos'@'localhost' IDENTIFIED BY 'SmartPos@2026';
ALTER USER 'smartpos'@'localhost' IDENTIFIED BY 'SmartPos@2026';
GRANT ALL PRIVILEGES ON smartpos.* TO 'smartpos'@'localhost';
FLUSH PRIVILEGES;
```

The same file is available at `database/setup.sql`.

Change the database password before production.

Spring Boot creates/updates the required tables automatically on first run.

# 7. How offline checkout works

When the Windows PC has no internet:

1. The React UI is loaded from the local Spring Boot application in production.
2. Spring Boot runs on `localhost:8080`.
3. MySQL runs as a local Windows service.
4. Product/menu data is read from local MySQL.
5. Checkout writes the sale, sale items, payment and stock movements locally in one transaction.
6. The receipt prints through the Windows printer.
7. PDF invoice generation still works because PDFBox is local.
8. Email/cloud work remains queued/retries later.

A cash sale therefore does not depend on your ISP.

A bank/card terminal may still depend on its own bank/SIM/network rules; POS software cannot approve a bank transaction without the acquirer's supported connectivity method.

# 8. Manager stock override

If the cashier requests more tracked stock than the database shows, checkout returns a manager-authorization requirement.

The cashier payment modal accepts:

- Manager/Admin username
- Manager/Admin password
- Mandatory reason

The backend verifies the credentials and role. If approved, the sale proceeds, stock may become negative, and an audit record is created.

The same validation also covers ingredient shortages for recipe-managed menu items.

---

# 9. Recipe / ingredient inventory

Manager/Admin can select a prepared menu product and define ingredient quantities.

Example:

```text
Cappuccino
  Coffee Beans  18 g
  Milk          200 ml
  Sugar         5 g
```

When Cappuccino quantity 2 is sold, SmartPOS deducts 36 g beans, 400 ml milk and 10 g sugar rather than decrementing a fictional "cup stock".

Recipe products are automatically changed to non-direct stock tracking after a recipe is saved.

# 10. Receipt and invoice

## 80mm receipt

The cashier success screen contains a local printable receipt. It opens a dedicated print window with an 80mm-style print layout.

Configure the Windows print driver to use the correct roll size and margins.

## A4 PDF invoice

The Java backend creates the invoice through Apache PDFBox:

`GET /api/invoices/{saleId}/pdf`

The UI downloads it using the actual completed transaction data.

---

# 11. Invoice email queue

`POST /api/invoices/{saleId}/email`

If SMTP succeeds, status becomes `SENT`.

If SMTP/internet is unavailable, status becomes `FAILED/PENDING` and the scheduled retry worker attempts delivery again. The completed sale is never rolled back because email failed.

# 13. Local backup

SmartPOS invokes MySQL `mysqldump` using the configured executable.

Default schedule:

`23:59 every day`

Default Windows folder:

`C:\SmartPOS\Backups`

Admin can also select **Create Backup Now** from the System page.

If `mysqldump.exe` is not on PATH, set:

```text
SMARTPOS_MYSQLDUMP_PATH=C:\Program Files\MySQL\MySQL Server 8.4\bin\mysqldump.exe
```

A controlled restore helper is supplied at `scripts/windows/restore-backup.ps1`. Always test restore into a safe environment before relying on backup procedures.

# 14. Build one local production application

From PowerShell:

```powershell
scripts\windows\build-all.ps1
```

This:

1. Installs/builds the React frontend.
2. Copies `frontend/dist` into Spring Boot static resources.
3. Packages the Java backend.

Result:

`backend\target\smartpos-backend-1.0.0.jar`

Run:

```powershell
java -jar backend\target\smartpos-backend-1.0.0.jar
```

Then open:

`http://localhost:8080`

Because frontend + backend + database are all local, the application continues to load and work when the internet connection is disconnected.

# 15. Windows Cashier auto-start

After a successful production build run PowerShell as Administrator:

```powershell
scripts\windows\install-autostart-task.ps1
```

At Windows logon, SmartPOS launches and opens `http://localhost:8080`.

For a dedicated commercial terminal, combine this with a restricted Windows `Cashier` account, separate Windows Administrator account, browser full-screen/kiosk configuration and protected MySQL/service permissions.

# 19. External integrations to finish for a specific customer

The code deliberately leaves vendor-specific behavior configurable rather than hardcoding one supplier. For a customer deployment, select and test:

- Real SMTP provider/application password.
- Actual 80mm ESC/POS printer model and Windows driver.
- Cash-drawer port/command through the chosen receipt printer.
- Bank/card terminal integration if the bank exposes an approved POS integration API/protocol.
- Real cloud endpoint if centralized multi-branch synchronization is required.
- Optional remote device-monitoring agent/service.
- Local tax/fiscal rules that apply to the customer's registered business.
- Restaurant kitchen screen/printer workflow if required at that site.

These integrations depend on the customer's chosen hardware/provider and cannot safely be guessed.
